## UX findings from this pass

This was a heuristic task walkthrough in the actual ordinary-Chrome panel, supported by source inspection and the regression suite, not a participant study or a new assessment of the inference engine. The intended job is to let a reader explore the author's current attention, broader learned/hierarchical organization, and recurring preferences, then inspect the evidence without losing their place. The local project brief, the supplied theory/engine review, and relevant definitions in Sounding Line's `THE_TRIPLE_INFERENCE.md` informed that framing. The existing local checkout was available; no clone or scientific run was needed.

Observed receipts and screenshots are in `evidence/ux-audit.json`, `ux-chrome-idle.png`, `ux-chrome-search.png`, `ux-shared-branch.png`, `ux-evidence-hover.png`, and `ux-list-fallback.png`.

1. **Highest priority: make spatial relationships faithful.** The authored “Make inclusion tangible” node reaches both story and practical-care, then purpose. Those references are present and highlighted, but independent row partitioning does not reserve contiguous child bands for each parent. Adjacency and the outline can imply the wrong grouping. A future layout should allocate branch-aware child bands and, where a shared semantic node needs two placements, use distinct linked visual instances instead of one tile crossing the fork. Kept deferred in this pass, including the supplied graph relationships.
2. **Make uncertainty inspectable.** The selected parent produces four possible sentence goals, two broader alternatives, and two possible endings. Blurring communicates ambiguity but hides the candidates. Compact reels also truncate labels such as “Make inclusion tangible.” Offer a click/focus expansion that lists full candidate names and evidence, retaining the compact reel at rest. Keep absence of an inference distinct from competing inferred alternatives and a path that has ended.
3. **Preserve reading position when dismissing details.** The walkthrough pinned a sentence, opened a value's evidence, and pressed Escape. Both the evidence and the lock disappeared. Recommend that Escape first close the topmost overlay; a subsequent Escape or explicit green lock should release the source selection. This behavior was observed and left for the next interaction pass.
4. **Teach the interaction without adding permanent chrome.** Moving from an unpinned sentence into the panel clears the cloud, so inspecting a phrase requires knowing to click first. A short optional first-use demonstration of hover → click to hold → inspect → unlock would preserve the requested idle cue and three-box design. Wheel navigation also needs a discoverable keyboard-equivalent explanation.
5. **Provide a stable reading surface for long explanations.** The value hover card occupied about 45% of the 899px-tall panel and passes pointer events through. That preserves access to other rows, but moving toward the explanation can dismiss it or activate what lies underneath. Keep passive previews concise and make full evidence/help explicitly openable and dismissible. Existing click-to-open value evidence is a useful foundation; heading explanations need an equally obvious stable route. [W3C's hover/focus guidance](https://www.w3.org/WAI/WCAG22/Understanding/content-on-hover-or-focus.html) discusses these persistence, hoverability and dismissal needs. This is not a conformance certification.
6. **Improve precision and legibility through an optional reading mode.** Observed attention text ranged roughly 8–30px; the smallest rectangular brick bounds were about 19.5px tall before clipping. Keep the expressive cloud, but offer local focus enlargement, branch zoom/keyboard traversal, and an easier-to-find readable view. The current list has all nodes but flattens their organization; nesting or a path display would make it a stronger alternative. [W3C's target-size guidance](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) gives a 24px baseline with defined exceptions, so dimensions alone are not a full compliance test.
7. **Expose meaning where a user commits to an interpretation.** Preserve separate attention data and stable values. In detailed inspection, explicitly distinguish a local role, broader goal, learned capability/habit, and a proposed production event. The middle heading currently names more than the graph itself displays. Keep score semantics beside the enlarged wheel: relative support and calibrated reliability should not become visually interchangeable when the backend arrives. Author, source, revision and selected evidence scope should remain grouped in the existing menu/inspection surfaces, without adding a fourth panel.
8. **Define the scope of world before connecting it.** Its current placement suggests a values-only switch; a future outside-context view or whole-reader world view would imply different behavior. Search is intentionally typing-only in this pass. Decide its eventual scope—values, hypotheses, source passages, or evidence—before making it perform a query.

Recommended next order: branch-aware geometry; full candidate inspection and overlay dismissal; a brief first-use guide and readable/keyboard path. Then test with people who have not seen the walkthrough: identify a sentence's proposed attention, follow it to a broader goal, explain why an alternative remains possible, inspect a source, and return to the same selection. Observe errors and successful completion, and ask which outputs are supplied hypotheses rather than established facts. Comparison against a plain prose account can test whether the spatial reader improves understanding. These are proposed evaluations, not results.

## Review loop

Double-click **ToMpathy Review** on the desktop, or `Review ToMpathy.cmd` here. Choose **Open the guided example**, then **Open Maker Reader**. Hover the article's second and fourth paragraphs to see different attention centers. Click a sentence, move away, scroll a reel, and release using either green lock. Hover the shared branch to see ambiguity on both sides; try the bottom tabs and search.

The launcher builds and restores/updates the extension in the persistent review Chrome profile. No server is needed for the bundled example. Bookmarks work during an open session; use the launcher after restarting Chrome/Windows to restore the development installation with the same ID. Save a reading session before replacing a build or closing the browser if its accepted account must be retained. The launcher does not pull, merge or publish automatically.

The private CI pipeline builds, tests core/browser/ordinary-Chrome flows, restores after restart and packages the tested ZIP. Work remains on `codex/author-first-testbed`; main is unchanged.
